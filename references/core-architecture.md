# Архитектура ядра

Содержание: границы; компоненты; БД; обработка; проверки; Make.com; эксплуатация; этапы.

## Границы

Владелец загружает Plaud пакетно раз в 3–5 дней. Формат и точный набор результатов пока не выбраны. Для первого парсера нужен реальный образец. Протоколы, поручения и сводки — кандидаты, а не разрешение на автоматическую рассылку.

MCP даёт доступ к инструментам и результатам, но не заменяет БД, очередь или кабинет. Make.com организует вызовы и уведомления; ядро хранит состояние и обеспечивает права, повторы, публикацию.

## Компоненты

| Компонент | Ответственность |
|---|---|
| core.registry | Один каталог ToolSpec |
| core.dispatcher | Авторизация, схемы, идемпотентность, результат, аудит |
| core.auth | Проверенная identity → tenant context |
| core.database | Tenant-scoped repositories, транзакции, миграции |
| core.jobs / outbox | Фоновые задания и надёжная отправка событий |
| core.adapters | HTTP/function calling и официальный MCP SDK |
| plugins/domain | tools, handle, своя схема и миграции, адаптеры регистрации |
| workers | Разбор, ИИ-обработка, проверка |

Два наружных представления опираются на один реестр. Домен включается после проверки контракта и миграций. Не исполнять произвольный Python, загруженный пользователем как «плагин».

| Таблица | Назначение |

| meetings.transcript_versions / segments | Версии текста, спикеры, таймкоды и происхождение |

| core.check_results | run, revision, check_no 1..4, verdict, причины, источники |

| core.jobs | Попытки, lease, checkpoint, next_retry_at |
| core.idempotency | Organization, operation, key, arguments_hash, результат |
| core.outbox / audit_log | Доставка событий и аудит действий |

Tenant-поля и составные FK обязательны по plugin-contract.md. Аудио/архивы — в object storage; выдавать короткоживущие ссылки после проверки прав. SQLite допустима локально, её тесты не подтверждают RLS/конкурентность PostgreSQL.

Если ID источника стабилен, ключ записи `(organization_id,source,source_account_id,external_id)`. Иначе использовать hash содержимого с сохранением происхождения. Не объединять разные организации/аккаунты по global plaud_id.

Бинарный hash находит одинаковый файл, но не доказывает идентичность содержания разных форматов. Семантическое сходство — лишь сигнал возможного дубля. Исправление текста создаёт новую версию и run.

## Пакетная обработка

Загрузка → регистрация → сохранение исходников → поддерживаемый парсер → нормализация → проверка 1 → ИИ-извлечение → проверки 2–4 → публикация → outbox → уведомление.

Команда запуска быстро возвращает job_id/batch_id/status=queued. Ключ идемпотентности защищает повторную команду; checkpoint — повторную обработку. Каждый batch_item получает явный исход: обработан, известный дубль, повреждён, неподдерживаемый, требует уточнения.

Дубликат связывать с прежним проверенным результатом, сохраняя факт новой загрузки. Актуальные пакетные проверки всё равно выполнить; проверка hash не заменяет четыре проверки. До публикации кабинет показывает статус и диагностику отдельно от проверенного результата.

## Четыре проверки

| № | Объект и критерий | При проблеме |
|---|---|---|
| 1 | Каждый вход и состав пакета: всё учтено/читается, части не потеряны, дубли связаны | blocked_ingestion с файлом и причиной |
| 2 | Каждый факт: имя/сумма/срок/поручение подтверждены исходником и сегментом/страницей | needs_review, исправление создаёт версию |
| 3 | Пакет и доступная история организации: противоречия, повторные задачи, связи проектов | needs_review, сохранить оба утверждения и источники |
| 4 | Итог: полнота, подтверждённость, разрешённые замечания и пройденные проверки 1–3 | не публиковать как проверенное |

Четыре повторения одного промпта не реализуют эти проверки. Сочетать детерминированные проверки, ИИ-оценку и сверку с источником. Положительный ответ модели не гарантирует фактической верности.

Публикационный барьер атомарно проверяет: текущий run, совпадающие входная/выходная revision/hash, четыре verdict=pass и отсутствие существенных неразрешённых замечаний. Четыре строки любых run не годятся. Уникальность `(organization_id,run_id,artifact_revision,check_no)` и ссылки на upstream revision не позволяют смешивать старые pass.

Изменение входа инвалидирует зависимые проверки; изменение результата — проверки 2–4. При изменении состава пакета пересчитать полноту. Ручное исправление запускает необходимые проверки повторно, а не обходит барьер.

Проверки отдельных записей дополнить проверками всего пакета. Не говорить «пакет прошёл», если часть записей пропущена или зависла. failed/blocked/review видимы в кабинете.

## Make.com

Проектируемые сценарии; названия модулей/ограничения перепроверить при сборке:

1. Приём: Custom webhook получает batch_id после сохранения файлов → HTTP создаёт run с Idempotency-Key → журнал job_id.
2. Завершение: подписанное событие outbox → проверка event_id/организации в ядре → Router published / needs_review / failed → кабинет и настроенный канал уведомления.
3. Восстановление: расписание → HTTP получает отложенные/зависшие jobs → разрешённые ограниченные повторы → уведомление об исчерпании попыток.

Большие файлы не переносить через каждый модуль: ID/метаданные/авторизованная ссылка. Webhook не доверяет organization_id из тела. Подпись и подключение определяют организацию; event_id защищает от повторных уведомлений.

Make.com не обеспечивает транзакцию с нашей БД. Авторитетное состояние — в ядре. Ошибка не должна превращаться в фиктивный успех. Blueprint, цены и лимиты не обещать до проверки тарифа/соединений.

## Эксплуатация

- Начать с PostgreSQL jobs с атомарным claim/lease; отдельный брокер добавлять по нагрузке.
- 429/сеть: ограниченные повторы с backoff; 401: исправление подключения; невалидный вход: без бесконечных повторов.
- Учитывать бюджет по пакету/организации/run, usage каждого ИИ-шага. Тайм-аут не доказывает отсутствие внешнего эффекта.
- Команды внутри записей не меняют инструменты, права, адресатов и публикацию.
- Защитить секреты/исходники по ролям. До реальных разговоров определить хранение и поставщиков обработки; облачный путь не называть локальным.
- Логи: batch_id/run_id/request_id, версии, время, повторы, стоимость, исход файлов. Полные разговоры по умолчанию не логировать.

## Этапы

1. Контракт, четыре references, генератор, проверка экспортов.
2. Рабочее ядро, один домен, auth, PostgreSQL и миграции.
3. Реальный формат входа и четыре проверки.
4. Кабинет и внешние клиентские подключения.

Завершение этапа 1 не означает готовность публичного URL, БД, настроенного Make.com или ИИ-конвейера. Продолжать по текущему запросу пользователя после завершения этапа.
