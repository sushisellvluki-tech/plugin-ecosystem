# Синтетический нагрузочный прогон

Запуск выполняется на отдельной одноразовой PostgreSQL 16 в GitHub Actions.
Реальные файлы, разговоры, токены владельца и платные ИИ-вызовы не используются.
Нагрузочный клиент создаёт локальный Uvicorn-сервер с настоящим HTTP и MCP SDK.

## Повторить

Подготовьте одноразовую БД и ограниченную роль по `docs/postgres.md`.
Задайте `TEST_DATABASE_ADMIN_URL`, `TEST_DATABASE_URL` и
`TEST_DATABASE_DISPOSABLE=yes`, затем:

```bash
python -m unittest discover -s tests -v
python -m scripts.stress_test --levels 1,8,32,64 --report stress-report.json
```

Скрипт создаёт только синтетические организации, но миграции относятся ко всей
указанной БД. Не направляйте эти переменные на рабочую БД. Автоматического удаления
пользовательских записей нет; CI уничтожает одноразовый контейнер после прогона.
Отчёт содержит только параметры, счётчики и задержки, без токенов и исходников.
GitHub Actions сохраняет JSON также в журнале под меткой `STRESS_RESULT`.

## Нагрузка на каждой ступени

- 4 изолированные организации, по 8 входных текстов.
- Каждый из 32 импортов отправляется трижды с одним ключом, вперемешку.
- Затем все 32 текста отправляются с новыми ключами: новые факты загрузки,
  прежние версии исходников.
- 32 изменённых тела с занятыми ключами должны вернуть `409 CONFLICT`.
- 32 попытки прочитать пакет другой организации должны вернуть `404 NOT_FOUND`.
- По два черновика на организацию проходят синтетическое подтверждение от
  отдельного тестового проверяющего и конкурируют за публикацию.
- Ровно одна публикация на организацию успешна; вторая устаревает по истории.
- Повторы успешных публикаций не создают новых событий.
- Настоящие MCP-клиенты читают все 32 пакета и сравнивают текст с входом.

Итого 252 измеряемых вызова на ступень, 1008 на четыре ступени. Служебные
MCP-сообщения подключения не входят в число вызовов инструментов.
После каждой ступени отдельный запрос к БД сверяет: 64 пакета, 32 версии исходников,
8 runs, 4 публикации и наличие outbox для каждого события. Любое расхождение,
неожиданная ошибка, утечка или несовпадение ответа делает прогон неуспешным.
Ожидаемые 409/404 учитываются отдельно и не скрывают неожиданные отказы.

## Управляемый отказ

Интеграционный тест удерживает транзакционную блокировку организации и сокращает
тайм-аут вызова. Проверяется HTTP 503 с `retryable=true`, отсутствие частичных
записей и успешный повтор с тем же ключом после освобождения блокировки.
Исправлена обработка кодов: `DEPENDENCY_UNAVAILABLE` → 503, `RATE_LIMITED` → 429;
неизвестная ошибка больше не маскируется под HTTP 200.

## Как читать показатели

Задержка измеряется от начала разрешённого клиентским семафором вызова до ответа;
ожидание очереди перед семафором исключено. Пропускная способность — измеряемые
вызовы, поделённые на полное время ступени, включая служебное подключение и проверки.
`peak_in_flight` показывает реально достигнутую параллельность.

Это ограниченный нагрузочный прогон, а не найденный предел сервера и не SLA.
Не проверены WAN/TLS, внешний прокси, многодневная работа, аварийное убийство
процесса, большой объём истории, реальный Plaud-парсер и качество ИИ.
Успех с 64 запросами не означает, что 65-й откажет, или что 64 — рабочая норма.
Горизонтальное масштабирование, пул БД и ограничение входной очереди — отдельные
изменения по измеренным требованиям; этот прогон их не подменяет.

## Проверенный результат — 2 октября 2026 (Красноярск)

[CI run 36922901178](https://github.com/sushisellvluki-tech/plugin-ecosystem/actions/runs/36922901178),
PostgreSQL 16, Python 3.12.14, runner с 4 логическими CPU. Все 60 тестов прошли
без пропусков; все четыре ступени нагрузки прошли проверку инвариантов.

Всего 1008 измеряемых вызовов: 736 успешных, 144 ожидаемых конфликта и 128
ожидаемых отказов в доступе к чужому пакету. Неожиданных ошибок — 0.
На каждой ступени независимая сверка БД подтвердила ожидаемые количества объектов
и отсутствие событий без outbox. Размер каждого синтетического текста — 5188 байт.

В этом сценарии после параллельности 8 пропускная способность почти не увеличилась,
а задержки выросли. Это наблюдение совместимо с ограничениями сериализации записей
по организации и затратами соединений; точная причина не установлена профилированием.
Для первого пилота разумен клиентский лимит 8 одновременных операций с последующим
замером на реальном окружении. Этот лимит не установлен автоматически в сервере.
