# Закрытый пилот: развёртывание и два доступа

Комплект запускает PostgreSQL 16, одноразовые миграции и HTTP/MCP-сервер с кабинетом.
Внешний адрес и постоянный сервер ещё не выбраны. Docker-стенд предназначен для закрытой проверки на синтетических данных; реальный экспорт Plaud пока не подключён.

## Запуск

Нужны Linux/macOS с Docker Compose v2 и Python 3.12. Команды выполняются из корня репозитория. Для Python используйте отдельное виртуальное окружение.

```bash
python -m pip install -r requirements.txt
# Родитель каталога должен существовать; сам каталог создаётся новым, вне репозитория.
python -m deploy.prepare "$HOME/plugin-pilot-private" --org pilot --name 'Пилотная организация'
export PILOT_SECRETS_DIR="$HOME/plugin-pilot-private"
python -m deploy.manage start
```

Открыть `http://127.0.0.1:8000/cabinet`. При необходимости задать `PILOT_HTTP_PORT` перед запуском.
Сохранить выбранные `PILOT_SECRETS_DIR`, `PILOT_HTTP_PORT` и `COMPOSE_PROJECT_NAME` в приватном окружении администратора: все последующие команды должны использовать те же значения.

База не публикует порт. HTTP привязан только к `127.0.0.1`, БД и bootstrap используют изолированную внутреннюю сеть. Приложение дополнительно подключено к обычной bridge-сети для публикации localhost-порта; его исходящий доступ в интернет не блокируется. На удалённой машине для закрытой проверки можно использовать SSH-туннель, например `ssh -L 8000:127.0.0.1:8000 user@server`. Открытый адрес потребует отдельного решения по HTTPS, reverse proxy и спискам разрешённых host/origin; текущая конфигурация его не создаёт.

## Разделение доступа

| Доступ | Файл в приватном каталоге | Возможности |
|---|---|---|
| Автор | `author.key` | Чтение, загрузка, подготовка результатов, публикация после успешных проверок |
| Проверяющий | `reviewer.key` | Чтение и независимое подтверждение; без загрузки и публикации |

Передавайте каждому участнику только его ключ по приватному каналу. В кабинете он вводится как токен. По умолчанию ключи действуют 7 дней (`--hours`, максимум 720 часов). Открытые ключи не выводятся в терминал и не входят в конфигурацию сервера: она содержит хеши и срок действия. Это два пилотных доступа, а не система регистрации пользователей или восстановления паролей. Продление/замена ключей пока требует контролируемого обновления конфигурации и пересоздания контейнера приложения; повторная генерация каталога с новыми паролями поверх существующей БД не поддерживается.

Приватный каталог имеет права `0700`, файлы ключей — `0600`. Файлы, монтируемые Docker, имеют `0444` внутри защищённого каталога для чтения непривилегированным UID 10001. Приложение получает только строку подключения ограниченной роли и хеши токенов. Пароли администратора доступны только БД и одноразовым административным командам. Доступ к Docker/этому каталогу эквивалентен административному доступу; не публикуйте их содержимое.

Немедленно отозвать доступ:

```bash
python -m deploy.manage revoke author
# Или: python -m deploy.manage revoke reviewer
```

Отзыв действует через членство в БД, в том числе для уже выданного токена. Перезапуск bootstrap не восстанавливает отозванное членство.

## Готовность и сохранность

`/healthz` проверяет процесс. `/readyz` возвращает 200 только при доступной БД, необходимых таблицах и ограниченной роли; иначе 503. Приложение запускается после готовности БД и успешных миграций. Том БД переживает остановку и перезапуск.

```bash
python -m deploy.manage status
python -m deploy.manage stop
python -m deploy.manage start
```

Не удаляйте Docker volume с рабочими данными. Диск и резервные копии требуют защиты на уровне выбранного хостинга; автоматического шифрования и удалённого хранения этот комплект не настраивает.

## Резервная копия и проверка восстановления

Укажите новый файл в существующем приватном каталоге:

```bash
python -m deploy.manage backup "$PILOT_SECRETS_DIR/pilot-001.dump"
python -m deploy.manage restore "$PILOT_SECRETS_DIR/pilot-001.dump" restore_trial_001
```

Создаётся `pg_dump` custom format с правами `0600` и SHA-256 рядом. Восстановление проверяет контрольную сумму, допускает только **новую** БД `restore_*` и не переключает рабочую строку подключения. При неудаче новая БД может остаться для диагностики. Восстанавливаются данные, схема и политики RLS; кластерные роли и приватные файлы доступа требуют отдельного сохранения. Для нового сервера сначала нужен bootstrap ограниченной роли. Переключение на восстановленную БД — отдельная плановая операция после проверки содержимого и прав.

Копия на том же диске помогает проверить восстановление, но не защищает от потери сервера. Расписание, зашифрованное внешнее хранилище, срок хранения и процедура аварийного переключения определяются после выбора хостинга.

## Проверки комплекта

Workflow `.github/workflows/pilot.yml` запускает настоящий Docker Compose с одноразовыми синтетическими ключами. Проверяет доступы, UID приложения, отсутствие административных секретов в приложении, сохранение данных и идемпотентности после перезапуска, резервную копию и восстановление в отдельную БД, отзыв доступа и сохранение отзыва после bootstrap. CI удаляет только свой одноразовый том.

Основной PostgreSQL workflow дополнительно проверяет доменные тесты, стресс-прогон и полный сценарий кабинета в Chromium. Публичный CI не использует данные владельца фирмы.

Справочные документы: [Compose startup order](https://docs.docker.com/compose/how-tos/startup-order/), [Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/), [PostgreSQL pg_dump](https://www.postgresql.org/docs/16/app-pgdump.html).
