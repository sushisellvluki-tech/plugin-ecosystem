# Meetings: текстовый пакет и проверяемая публикация

Этот этап реализует хранение и проверку **явно переданных текстовых расшифровок**.
Нативный формат экспорта Plaud ещё не подтверждён образцом. PDF, ZIP, аудио,
автоматическое распознавание и обращения к модели здесь не реализованы.
Поддерживаемый вход — JSON со строками `text/plain`, а не загрузка бинарного файла.
Исходник сохраняется как переданный Unicode-текст без нормализации пробелов/переносов;
это не обещание побайтового сохранения неизвестного исходного файла.

## Запуск

Плагин `plugins.meetings.plugin` уже включён в репозиторий. Не генерируйте его
повторно: генератор правильно откажется перезаписывать существующий каталог.
Установите зависимости, выполните миграции по [postgres.md](postgres.md), затем
запустите хост по [server.md](server.md) **без `--demo`**, с `DATABASE_URL`.
Миграция `002_meetings.sql` применяется тем же административным мигратором;
рабочая роль не владеет таблицами и не имеет BYPASSRLS.

Для организации включите домен `meetings` и назначьте права в БД и токене:

| Право | Действия |
|---|---|
| `meetings:read` | Каталог, исходники пакета, черновики, проверки и история публикаций |
| `meetings:write` | Приём пакета и новая версия черновика |
| `meetings:review` | Подтверждение точности, полноты и согласованности независимым проверяющим |
| `meetings:publish` | Публикация после четырёх pass |

Проверяющий должен иметь другую `actor_id`, чем автор черновика. Его учётные
данные не выдавайте автоматическому извлекателю: сервер проверяет отдельную
идентичность и права, но не может доказать, что человек действительно прочитал текст.
Каждый изменяющий вызов требует `Idempotency-Key`. Повтор того же вызова с тем же
ключом возвращает исходный результат, а не обновлённый статус; актуальный статус
получайте через `get_run`.

## Порядок вызовов

Через HTTP используйте `POST /meetings/v1/tools/invoke` с `{name, arguments}`.
Те же инструменты доступны через `/meetings/mcp`.

1. `meetings__import_batch`:

```json
{
  "source_account_id": "my-manual-plaud-export",
  "sources": [{
    "filename": "meeting.txt",
    "format": "text/plain",
    "text": "Иван сдаст отчёт в пятницу.",
    "external_id": "recording-001"
  }]
}
```

Ответ содержит `batch_id` и явный исход каждой записи: `accepted`, `duplicate`
или `rejected`. Неизвестный формат/пустой текст блокирует весь пакет для обработки,
но сохраняется в его составе с причиной. Текст с NUL отклоняет запрос целиком:
PostgreSQL text не может сохранить такой исходник без изменения.

Пределы: 1–20 элементов и 32 КиБ текста UTF-8 в сумме; также действует общий
лимит аргументов ядра 64 КиБ. Большие пакеты и object storage — следующий этап.
`external_id=null` разрешён: идентичность определяется хешем текста внутри аккаунта
и организации. При стабильном ID исправление создаёт новую версию; совпадение с
последней версией — дубль. Переход A → B → A создаёт третью версию.

2. `meetings__submit_draft`:

```json
{
  "batch_id": "UUID из первого ответа",
  "claims": [{
    "source_index": 0,
    "start": 0,
    "quote": "Иван сдаст отчёт в пятницу.",
    "text": "Иван сдаст отчёт в пятницу.",
    "subject": "Отчёт Иван",
    "predicate": "срок",
    "value": "пятница"
  }],
  "model_version": null,
  "prompt_version": null
}
```

`start` — позиция в исходной Python/Unicode-строке, с нуля, не UTF-8-байт и не
UTF-16 offset. `source_index` соответствует порядку файлов пакета. Каждая цитата
должна точно совпасть по позиции; каждый источник должен иметь хотя бы один claim.
Это структурная проверка охвата, а не доказательство смысловой полноты.
Не более 50 claims. Предложение текста вручную или внешней моделью не запускает
скрытых сетевых вызовов. `model_version`/`prompt_version` — заявленное происхождение,
не доказательство вызова модели. При ручной работе оставляйте `null`.

3. Проверяющий читает `meetings__get_batch`, `meetings__get_run` и
   `meetings__get_history`, затем вызывает `meetings__review_run`:

```json
{
  "run_id": "UUID черновика",
  "artifact_hash": "хеш из ответа submit_draft",
  "accuracy_pass": true,
  "consistency_pass": true,
  "coverage_confirmed": true,
  "rationale": "Что проверено по исходникам и истории; как разрешены замечания"
}
```

`true` ставится только после соответствующей проверки. Отрицательные результаты
сохраняются и блокируют публикацию. Сломанную цитату или обнаруженное противоречие
нельзя переопределить подтверждением: исправьте claims и создайте новый run.

4. `meetings__publish` принимает `{run_id, artifact_hash}`. В одной транзакции он
   повторно проверяет актуальность и четыре pass одного run, сохраняет публикацию,
   событие `meetings.published` и outbox. Никакие уведомления не отправляются.

## Что означает каждая проверка

| № | Автоматика | Подтверждение проверяющего |
|---|---|---|
| 1 | Все заявленные элементы сохранены, поддерживаются и связаны с версиями | Проверка полноты самого экспорта вне системы |
| 2 | Точные цитаты/позиции, обязательные поля, охват источников | Смысловая точность и полнота извлечённых фактов |
| 3 | Разные значения одного subject/predicate в пакете и опубликованной истории | Контекст, даты, неявные противоречия и связи |
| 4 | Актуальные pass 1–3 и подтверждение полноты | Основание — сохранённая независимая аттестация |

Автоматического ИИ-проверяющего пока нет. Совпадение цитаты не делает утверждение
истинным. Проверка одинаковых ключей намеренно консервативна: разные периоды/проекты
следует явно различать в subject/predicate нового черновика и повторно проверять.
История ограничена 100 опубликованными версиями; при превышении `truncated=true`
и новая публикация блокируется до расширения механизма просмотра/проверки истории.

## Версии и защита от старых подтверждений

Исходники, состав пакета, claims и результаты каждой проверки сохраняются по
версиям. Новый черновик меняет текущий run пакета. Изменение текста стабильного
источника делает прежний run устаревшим. Новая публикация в организации делает
неопубликованные runs со старой историей устаревшими. Нужен новый run и проверка.

Исторические публикации не удаляются. `get_history`/`get_run` отмечают `stale`,
если исходник или текущий черновик уже изменился; такие результаты нельзя выдавать
за актуальные. Публикации в истории учитываются консервативно, включая устаревшие.

Записи сериализуются внутри организации транзакционной advisory-блокировкой;
организации независимы. RLS дополнительно проверяет organization и domain.
Core Item служит общим якорем событий; его общий `status` не является статусом
run — используйте API домена. В outbox не копируются полные разговоры.

До реальных разговоров ещё нужны: образец Plaud, решение о хранении/удалении,
выбранный поставщик ИИ и бюджет, обработка больших файлов и интерфейс проверяющего.

59 тестов прошли без пропусков на PostgreSQL 16. Проверены настоящие MCP-вызовы

реального Plaud-парсера или ИИ-извлечения, которые ещё не подключены.
